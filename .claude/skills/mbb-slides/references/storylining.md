# Storylining (the Minto method, applied)

The deck is an argument, not a document dump. Storyline first, slides second.
This is where MBB decks are won or lost.

## The pyramid

```
                 Governing thought (the answer)
                /            |            \
          Branch 1       Branch 2       Branch 3      ← MECE
          /     \        /     \        /     \
      evidence evidence  ...            ...           ← each = one slide
```

- **Governing question** — the single question the audience is asking. One
  sentence, ends in a question mark. "Should we enter the German market in
  2027?"
- **Governing thought** — the answer, stated as a claim, up front. "Enter
  Germany in 2027 through acquisition, not greenfield — it's 18 months faster
  to break-even." This is the exec-summary line and the spine of the deck.
- **Branches** — the 2–4 reasons the governing thought is true. They must be
  **MECE**: mutually exclusive (no overlap) and collectively exhaustive (nothing
  material missing). Three is the natural number; two feels thin, five means the
  grouping is wrong.
- **Evidence** — each branch is proven by 1–N slides, each carrying one claim.

## Action titles

The title *is* the message. Rules:

- Complete sentence with a verb. "Costs fell 12% after the 2025 consolidation"
  — not "Cost Trends."
- States the conclusion, not the topic. The reader should not have to look at
  the chart to know the point; the chart proves a point they already read.
- Quantified where possible. "Three of five segments are unprofitable" beats
  "Segment profitability varies."
- ≤2 lines. If it needs three, the message is doing too much — split the slide.
- Consistent grammatical form across a section reads as rigor.

## The two tests

1. **Headline-flow test.** Extract every action title into a list, in order.
   Read only that list. Does it argue the governing thought start to finish,
   with no body content? If a reader can't follow the logic from titles alone,
   the storyline is broken — fix it before touching a single slide.

2. **So-what test.** For every slide, ask "so what?" until you hit a decision or
   an action. If the answer to "so what?" is another fact, the slide hasn't
   reached its point yet. Push the title down to the implication.

## Deck structures by type

- **Recommendation:** Situation → Complication → Question → Answer (SCQA) up
  front, then the governing thought, then branches as the *reasons*, then
  implementation/risks. The classic McKinsey shape.
- **Readout / update:** Governing thought = the headline status. Branches =
  workstreams. Lead each with its status, not its activity.
- **Case-study / proof:** Governing thought = the outcome achieved. Branches =
  problem, approach, result. Use the proof-slide skeleton (see SKILL.md).
- **Diagnostic:** Governing thought = the root cause. Branches = the drivers,
  structured as an issue tree (MECE decomposition of the problem).

## SCQA (the opening)

- **Situation** — the stable context everyone agrees on.
- **Complication** — what changed / what's now at risk. Creates the tension.
- **Question** — the governing question the complication forces.
- **Answer** — the governing thought.

Two or three sentences of S and C earn the audience's attention before you
state the answer. Skip them and the recommendation feels unmotivated.

## Common storyline failures

- **Chronological instead of logical.** "What we did in Q1, Q2, Q3" is a diary,
  not an argument. Structure by *reason*, not by *time*.
- **Grouping by data source instead of by insight.** "Survey findings / interview
  findings / financial findings" is MECE by method but useless to a decision-
  maker. Group by what the reader should conclude.
- **Answer last.** Building suspense to a reveal is for mysteries. Executives
  want the answer first, then the support. Pyramid, not funnel.
- **Overlapping branches.** If branch 2 and branch 3 share evidence, they aren't
  mutually exclusive — regroup.
